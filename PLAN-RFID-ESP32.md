# Plan: migración del nodo RFID de mini PC a ESP32

Objetivo: reemplazar el mini PC (Docker: `postgres` + `server` + `update_db`) por un nodo ESP32 offline-first con flash externa W25Q128, RTC DS3231 y sincronización con el backend `webRailway` vía AWS IoT + HTTPS.
Rama: `rfid-esp32` (sale de `rfid`; se une a `rfid` cuando esté estable). Firmware en `open_seguricel_programmer/firmware/rfid_server/` (ESP-IDF v6.1, rama `feat/servidor-rfid`; hasta L32 estuvo en `firmware/` de este repo, y las rutas `firmware/...` del Log se refieren a esa ubicación). Hardware de referencia: `especificaciones_del_sistema_de_control_de_acceso_rfid.md`.
Estado actual: **Fase 1 (prototipo de hardware) completa y validada en hardware. Siguiente: Fase 2 (núcleo offline).**

## Specs

### S1 — Paridad funcional con el sistema actual
El ESP32 debe hacer lo mismo que `servidor/codigo.py` + `scripts/*.py`:
- Recibir del ESP8266 `POST /{epc}/{dispositivo_id}/{descripcion}/seguricel_rfid_activo` y `POST /{dispositivo_id}/noregistrado`; `GET /seguricel_wifi_activo`. `dispositivo_id` es `dispositivos_informacion.id` del relé que abre esa antena (reemplaza al texto `acceso`, ver L10); el relé se busca con `id = dispositivo_id AND apertura = true`. Un id no numérico o desconocido se trata como "sin dispositivo de apertura" (no abre, log con `SIN_DISPOSITIVO_DE_APERTURA`).
- Validar: tag existe → activo → (vehículo → usuario) → permiso RFID → Propietario pasa siempre → horarios (`Siempre`, ventana del día, ventanas que cruzan medianoche, varias ventanas el mismo día).
- Abrir con `GET {dispositivo}/on`, denegar con `GET {dispositivo}/off`, registrar log (mismos campos que `logs_rfid`).
- Tags no encontrados no generan log (igual que hoy).
- Una lectura produce **una sola** apertura/denegación (corregido en `servidor/codigo.py`, commit `a97ebf8`).

### S2 — Decisiones del usuario (2026-11-20)
- Tag sin usuario asociado: "si debe abrir".
- Usuarios con horario cuando el equipo no tiene hora confiable: "se rechazan". Propietarios y `acceso_libre` sí abren.
- Cola de logs llena: "se pisan los mas viejos". Contador de logs perdidos en el latido (`status`).
- Framework: "ESP-IDF esta bien, ya tengo los entorno condifgurados".
- Capacidad: 32 filas de horario por usuario ("los 32 me parecen bien") y ~16.000 tags ("dejalo en 16000").

### S3 — Almacenamiento en la W25Q128 (16 MB, un solo LittleFS)
| Zona | Tamaño | Contenido |
|---|---|---|
| Tags | 2 × 3 MB (`/tags.bin` + `/tags_tmp.bin`) | ~16.000 registros de 192 B |
| Dispositivos | KB | `/dispositivos.bin` (id → IP relé, descripción, tipo_acceso, tipo_dispositivo; solo `apertura = true`) |
| Logs | ~9 MB | ~140.000 logs de 64 B (≈70 días sin internet a 2.000/día) |
| LittleFS | ~1 MB | metadatos |

**Registro de tag (192 B, ordenado por EPC → búsqueda binaria), implementado en `firmware/components/nucleo_rfid/`:** `epc` 12 B · `tag_id` 4 B · `codigo` 10 B (`varchar(10)`, 10 dígitos en el backend) · `flags` 1 B (activo, con_usuario, permiso_rfid, propietario: se guardan crudos para respetar el orden de las reglas de `codigo.py`) · `n_horarios` 1 B · 32 filas × 5 B (palabra de 40 bits: `dia` 3 bits, 0 = Lunes … 6 = Domingo, 7 = `Siempre`; `entrada` y `salida` 17 bits cada una, **segundos** desde medianoche, igual que compara `codigo.py`) · CRC-32 (como `zlib.crc32`).
Tags inactivos se incluyen (`activo = false`) para registrar "tag inactivo". Si un usuario supera 32 filas, el backend lo reporta (nunca recorta en silencio). Un tag con varios vehículos usa el primero (igual que el backend: `tag_vehiculos.first()`).
**Supuestos a confirmar:** (a) `Siempre` abre aunque la hora no sea confiable (no depende del reloj); (b) ~~`entrada == salida` es una ventana de un segundo~~ **decidido (L14):** `entrada == salida` se rechaza "fuera de horario" con log (`codigo.py` no abría ni registraba nada); (c) el EPC llega como 24 caracteres hex: el backend lo guarda como `CharField(255)`, así que un EPC de otro largo se rechaza y se reporta al armar la lista.

**Actualización atómica:** descargar a `/tags_tmp.bin` en bloques (soltando el mutex SPI entre bloques) → verificar cantidad + SHA-256 → `rename` a `/tags.bin`. Rechazar listas vacías o con caída > 50 % salvo marca explícita. Borrar `/tags_tmp.bin` huérfano al arrancar.

### S4 — Cola de logs (anillo en flash)
- Cada log lleva su `seq` (uint32, nunca vuelve a 0) y CRC dentro del registro.
- `siguiente` vive en RAM; al arrancar se reconstruye buscando el `seq` válido más alto en la flash.
- `confirmado hasta` se guarda en la EEPROM AT24C32 (0x57) con firma (magic) + CRC, **después** de recibir el ack, nunca antes. Atrasado es seguro (solo reenvía); adelantado perdería logs.
- Si la EEPROM es inválida (chip nuevo/dañado): reenviar todo lo que hay en flash; el backend descarta los duplicados por `evento_id` (L16).
- Al enviar, cada log lleva `evento_id = UUIDv5(device_id, seq)`, igual que los otros logs del backend.
- El anillo avanza por sector (4 KB = 64 logs); un sector solo se borra si sus logs están confirmados o si la cola está llena (política: pisar el más viejo).

### S5 — Hora
- DS3231 (0x68) + NTP. Venezuela UTC-4 sin horario de verano.
- Bit OSF del DS3231 encendido ⇒ hora no confiable ⇒ aplicar S2 (rechazar usuarios con horario) y marcar logs como "hora no confiable" hasta sincronizar por NTP.

### S6 — Concurrencia (FreeRTOS)
- Core 1 (alta prioridad): recibir EPC → hora → buscar en `/tags.bin` → relé → encolar log.
- Core 0: WiFi, MQTT, subida de logs, descarga de lista.
- Mutex obligatorio para el bus SPI / LittleFS. La cola llena o la nube caída nunca bloquean la apertura.

### S7 — Nube (backend `webRailway`, integración AWS IoT existente)
| Topic / endpoint | Dirección | Uso |
|---|---|---|
| `seguricel/{device_id}/events/rfid` | ESP32 → AWS → Rule → `ioteventosapi/` | Lotes de ~50 logs, QoS 1 |
| `seguricel/{device_id}/cmd/ack` | backend → ESP32 | `{"upTo": seq}` acumulativo; recién ahí avanza `confirmado hasta` |
| `seguricel/{device_id}/cmd/sync` | backend → ESP32 | `{version, url}` cuando cambian tags/usuarios/horarios (agrupar cambios unos segundos) |
| `seguricel/{device_id}/status` | ESP32 → backend | Latido / Last Will (ya existe) |
| `GET rfidlistaapi/{device_id}/?v=&exp=&firma=` | ESP32 → Django (HTTPS) | Lista NDJSON ordenada por EPC, con encabezado (versión, cantidad) y pie (SHA-256) |

- Idempotencia: `evento_id` UUID con restricción única parcial en `logs.rfid`, como los otros logs (⚠️ migración sobre tabla con datos, en `webRailway`; revisar el tamaño de la tabla para decidir si el índice se crea `CONCURRENTLY`).
- Política de AWS IoT propia para RFID (`AWS_IOT_POLITICA_RFID`); `emitir_certificado` la elige según `sistema`.
- Consulta diaria de respaldo además de `cmd/sync`.
- `registrarlogsrfidapi` se mantiene para los mini PC existentes.

### S8 — Seguridad
- Política IoT: ampliar con publicar `events/rfid` y suscribirse/recibir `cmd/sync`, `cmd/ack`. El equipo nunca publica en `cmd/*`. Usuario IAM del backend: sumar publish a `cmd/sync` y `cmd/ack`.
- URL de la lista firmada con HMAC-SHA256 (secreto solo en Django), vence en ~10 min. El equipo no guarda `API_AUTH_USER/PASSWORD`.
- Red local (hoy sin autenticación, cualquiera en el WiFi abre con `curl .../on`): HMAC con contador anti-replay en ESP32 → relé y ESP8266 → ESP32; el relé responde ACK. WiFi dedicado WPA2 con clave única por instalación.
- Flash encryption (cubre solo la flash interna: certificado AWS, claves HMAC). `/tags.bin` en la W25Q128 requiere cifrado por software si se quiere proteger. Secure boot solo en producción.

### S9 — Configuración del nodo (NVS, la graba el programador)
Namespace `seguricel`, mismas claves que el controlador ESP32 (`open_seguricel_programmer/provision.py:199-239`): `device_name` (opcional), `wifi_ssid`, `wifi_pass` (puede ser ""), `ip`, `gateway`, `netmask` (strings; **IP fija**: la antena envía las lecturas a esa IP), `device_id`, `mqtt_url` (`mqtts://...:8883`), `mqtt_ca`, `mqtt_cert`, `mqtt_key` (binary, PEM). El servidor HTTP escucha en el puerto **43157**, el mismo de `servidor/codigo.py`. Sin `wifi_ssid` válido el nodo no arranca la red y lo informa por el monitor serie.

### S10 — Lista del nodo (endpoint de solo lectura, URL firmada)
- `GET rfidlistaapi/<dispositivo_pk>/?exp=<unix>&firma=<hex>`; `firma = HMAC-SHA256(RFID_LISTA_SECRETO, "<dispositivo_pk>:<exp>")` en hex. Rechaza (403) si `exp` ya pasó, si `exp` está a más de 15 min en el futuro o si la firma no coincide (comparación de tiempo constante). El dispositivo debe tener `sistema = 'rfid'` y `controlador`. Sin sesión ni Basic: la firma es la credencial.
- Respuesta NDJSON (`application/x-ndjson`), una línea JSON por registro, en este orden:
  1. Encabezado: `{"tipo": "encabezado", "version": "<sha256 corto del contenido>", "dispositivos": M, "tags": N, "errores": [...]}`.
  2. M líneas `{"tipo": "dispositivo", "id", "url", "descripcion", "tipo_acceso", "tipo_dispositivo"}`: los dispositivos del contrato con `apertura = true` (para abrir el relé y armar el texto de los logs).
  3. N líneas `{"tipo": "tag", "epc", "tag_id", "codigo", "activo", "con_usuario", "permiso_rfid", "propietario", "horarios": [["Lunes", "08:00:00", "17:00:00"], ...]}` ordenadas por `epc` en mayúsculas. `con_usuario`/`permiso_rfid`/`propietario` salen del **primer** vehículo del tag (`tag_vehiculos.first()`). Horarios: los del usuario visibles por el manager por defecto, sin mirar `fecha_entrada`/`fecha_salida` (igual que `codigo.py`).
  4. Pie: `{"tipo": "pie", "sha256": "<hex del SHA-256 de todos los bytes anteriores>"}`.
- Nunca se recorta en silencio: un tag con EPC que no sea de 24 hex, con más de 32 filas de horario o con un horario sin `dia`/`entrada`/`salida` se deja **fuera** de la lista y se reporta en `errores` (`{"tag_id", "codigo", "motivo"}`).
- `version` cambia si y solo si cambia el contenido.

### S11 — Sincronización por MQTT (adelantada, L17)
- Backend → `seguricel/<device_id>/cmd/sync`, QoS 1: `{"version": "<versión actual>", "url": "<URL firmada completa de S10>"}`.
- Cuándo: (a) comando manual `rfid_sync` (por dispositivo o por contrato); (b) cuando el nodo publica su latido en `seguricel/<device_id>/status` con una `lista` distinta de la versión actual (cubre el arranque y la consulta diaria). Los avisos automáticos por cambios en tags/usuarios/horarios quedan para después.
- El ESP32 descarga a `/tags_tmp.bin` y `/dispositivos_tmp.bin`, verifica cantidad + SHA-256 del pie, y recién entonces renombra (S3: rechaza listas vacías o con caída > 50 % salvo marca explícita).
- Política de AWS IoT propia (`AWS_IOT_POLITICA_RFID`): conectar con su `device_id`; publicar `events/rfid` y `status`; suscribirse/recibir `cmd/ack` y `cmd/sync`. `emitir_certificado` la elige según `sistema`. Fuera del código (consola de AWS, lo hace el usuario): permiso IAM del backend para publicar en `cmd/sync`/`cmd/ack`, y la IoT Rule de `status` si no cubre ya los nodos RFID.
